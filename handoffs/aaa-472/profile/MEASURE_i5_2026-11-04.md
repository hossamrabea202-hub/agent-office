# #487 Where the battle frame goes: measured on i5, 2026-11-04 13:50-14:05

i5 core (seat `checkking (Claude)`), i5-1235U + 2 GB MX570, UE 5.8.4, PIE in ThirdPersonMap. Read-only: console commands in Play only, nothing saved.
Tools: CSV profiler (`csvprofile start/stop`), Unreal Insights trace with named events (`Trace.File cpu,frame,bookmark` + `stat namedevents`), exported headless with `UnrealInsights.exe -ExecOnAnalysisCompleteCmd`.
Scripts are in this folder: `measure_split_ue.py`, `trace_wave_ue.py`, `csv_split.js`, `insights_timers.js`, `insights_bp_callers.js`. Raw summaries: `split_i5_1104_*.txt`, `insights_i5_1104_wave_timers.txt`.

**Caveat: i5's Blueprints are older than i9's.** Fixes A-D and F were applied only on i9 (BP_SoldierSword on i5 still has the CX_144 / CX_453 scans D removed). So the zombie scan costs below are partly fixed on i9 already. The soldier and HUD costs are not (see "Still live on i9").

## 1. The split (ms per frame)
| | zombies | Frame | Game thread | GPU | Render thread |
|---|---|---|---|---|---|
| No wave, editor in background | 0 | 333 (capped) | **38** | 75 | ~0 |
| Wave, editor in background | 111 | 333 (capped) | **132** | 64 | 0.8 |
| Wave, editor in front | 142 | **161** | **162** | 42 | 0.4 |

- **A wave is game-thread work.** Game thread 38 -> 132-162 ms; GPU stays 42-75 ms (and i5's GPU is the weak part). On i5 in a wave, frame = game thread.
- **The editor caps itself at 3 fps (333 ms) when it is not the front window.** The two background runs show FrameTime 333.3 ms flat with Game 38 / GPU 75: nothing in the game took 333 ms. **i9's "3-4 fps / 250-330 ms" may be this cap too.** Any measurement must be taken with the editor in front, or with Editor Preferences > General > Performance > "Use Less CPU when in Background" off.

## 3. Top 5 costs by name (Insights, 47 game frames, 142 zombies, 2-4 soldiers)
| # | What | ms / frame | Notes |
|---|---|---|---|
| 1 | **BP_SoldierSword ReceiveTick** | **30** | Only 2 soldiers ticking: ~15 ms each. Pure Blueprint VM time. Every frame each soldier loops over ALL zombies (CX_145: the whole fight logic per zombie, then CX_454 again). Cost = soldiers x zombies. With i9's 20-60 soldiers this alone can be most of the wave's ~200 ms (G: not measured on i9). |
| 2 | BP_Zombie Think + event graph | ~19 | Think on a timer. Inside: GetAllActorsOfClass ~5 ms, SimpleMoveToActor ~4 ms, GetActorOfClass ~3.4 ms (i5 copy is pre-fix-A; i9 has the registry). |
| 3 | Zombie CharacterMovement + skeletal mesh | ~13 + ~9 | 127 movement components and 170 skeletal mesh ticks a frame. |
| 4 | HUD chain (11 levels, BP_NoticeHUD down to BP_ZombieHUD) | ~12 | **BP_ZombieHUD calls LineOfSightTo 1035 times a frame (~8 ms)**: one per zombie, every frame. |
| 5 | Tag scans GetAllActorsWithTag | ~3-5 | BP_BarracksHUD, BP_CommanderHUD, BP_SoldierSword (fix J covers the soldier's). |

A Play-only ablation (switch one system off, measure) was **inconclusive**: base frames swung 41-207 ms while the wave grew from 129 to 230 zombies, and 15-20 Hz caps do nothing when a frame already takes 110-200 ms. Only "HUD not drawn" gave a usable read (106 ms vs 113-145 base), consistent with the trace's ~12 ms.

## 5. Fix handed to i9: K (soldier AI 15 Hz)
`handoffs/aaa-472/ops/README_K.md`. Expected: soldier AI cost on screen x 1/2 at 30 fps and x 1/4 at 60 fps. **No gain while frames are slower than 66 ms** (at 3-4 fps the soldier already ticks once per frame). It is a step towards 33 ms, not a cure on its own.
